# WholesaleHub AI Merchandising Automation

Date: 2026-09-02 KST
Status: source implementation and CI contract for PR #36. Production/runtime claims require the deployment marker and runtime smoke evidence described below.

## Purpose

When an approved WooCommerce product transitions from `draft` or `pending` to `publish`, WholesaleHub queues an asynchronous merchandising job. Publication itself never waits for AI.

The job has two independent outputs:

1. a newly composed product thumbnail generated by the ChatGPT-authenticated Codex CLI when built-in image generation is available;
2. structured Korean merchandising copy rendered by WordPress as editable HTML inside the product full description.

The current supplier thumbnail and base description are always the fallback. AI failure must not prevent publication or delete the fallback.

- Contracts: `tests/ai-merchandising-contract.test.mjs`, `tests/ai-merchandising-php.test.php`

There must be only one WordPress source of truth for the hook: the MU plugin above. Do not reintroduce a duplicate implementation under `avocadoss-performance`.

## Queue contract

The publish hook writes immutable job JSON under:

`wp-content/uploads/wholesalehub/ai-merchandising/queue`

Only public-safe fields are passed to Codex: product ID/name, public description, categories, a source hash and a relative path to the existing product image when available.

Do not add supplier names/IDs, supplier URLs, original source URLs, costs, margins, credentials or other private operational metadata to the Codex packet.

The source hash prevents redundant successful regeneration for an unchanged product state.

## Codex execution contract

The worker uses the local ChatGPT-authenticated `codex` executable, not provider API billing.

Before spawning Codex it unsets common API-key variables, including OpenAI, OpenRouter, Anthropic, Gemini/Google and Azure OpenAI keys. The worker must not contain direct provider API endpoints or SDK fallback logic.

Codex runs in `workspace-write` sandbox mode in an isolated per-job directory.

For images:

- the real current product image is copied into the isolated job directory when available;
- it is attached to Codex with `--image` and described as Product Ground Truth;
- the prompt explicitly invokes `$imagegen`;
- output must be a new ecommerce composition while preserving the real product identity;
- no unverified logo, certification, price badge, watermark or Korean text is baked into generated imagery;
- if built-in image generation is unavailable, Codex must not fake an image or call an API.

For copy:

- `output/copy.json` is required;
- 4–6 purpose-distinct sections are requested;
- unsupported price/origin/weight/specification/certification/shipping/review/sales/medical-efficacy claims are prohibited;
- placeholders such as `확인 필요` or `TODO` are prohibited.

## Failure semantics

Codex exit failure or missing `copy.json`:

- do not run the Woo apply script;
- quarantine the queue job under `failed` with diagnostic evidence;
- keep the published supplier image and base description unchanged.

Image generation failure after valid copy:

- apply the validated HTML copy;
- keep the supplier/current thumbnail;
- mark thumbnail status as fallback.

Thumbnail application failure:

- restore the previous thumbnail;
- remove an orphan generated attachment when safe;
- do not leave a partially applied AI thumbnail.

Detail application failure:

- retain the existing base description;
- never report detail success without read-back verification.

Failed jobs are quarantined rather than automatically retried forever. This prevents repeated Codex usage burn and repeated partial mutations.

## WooCommerce detail-page contract

AI copy is rendered to ordinary HTML text by WordPress, not baked into generated images. This preserves mobile readability, searchability and editability.

The managed block is bounded by:

- `<!-- wholesalehub-ai-detail:v1:start -->`
- `<!-- wholesalehub-ai-detail:v1:end -->`

A new successful generation replaces the previous managed block instead of appending duplicates. Supplier/base description outside the managed block is retained.

Later `wp_insert_post_data` updates preserve the managed block unless the AI apply path is intentionally replacing it.

## Thumbnail overwrite protection

A thumbnail is considered a valid AI thumbnail only when:

- product meta `_wh_ai_thumbnail_status` is `success`;
- `_wh_ai_thumbnail_attachment_id` equals the current featured image ID;
- the attachment is still a valid image.

The explicit catalog thumbnail repair script exits with `preserved_ai` for such products.

The AI attachment intentionally does not masquerade as a supplier image by setting `_wholesalehub_image_source_type`. Standard catalog sync therefore treats the valid unclassified current image as operator-owned and keeps it instead of replacing it with incoming supplier imagery.

If somebody manually replaces the featured image later, the stale AI marker no longer protects a different attachment.

## 24/7 scheduler

`install-runtime.sh` prefers a user-level systemd timer running every 60 seconds. It sets deterministic `HOME` and `PATH` values so the authenticated Codex binary can be resolved.

If the SSH/runtime context cannot access a user-systemd bus, the installer falls back to an idempotent user crontab entry every minute. The worker-level `flock` prevents overlap.

No global kernel/AppArmor/user-namespace weakening is authorized for this automation.

## Deployment contract

Production changes must go through `scripts/deploy-wholesalehub.ps1` from a clean checkout whose HEAD exactly equals `origin/main`.

The deployment wrapper:

- archives the exact GitHub HEAD;
- validates AI runtime inventory and shell syntax;
- backs up managed live WordPress plugins/MU files and rolls them back on deployment failure;
- deploys and PHP-lints the AI MU module;
- verifies normal homepage/search HTTP health;
- updates the MiniPC source mirror;
- installs/verifies the unattended scheduler;
- records `reports/runtime/deployed-github-head.txt`;
- can run `-RunAiSmoke` to prove the actual ChatGPT-authenticated Codex text and `$imagegen` runtime.

## Required release verification

Do not call the feature production-complete until all of the following evidence exists for the merged main SHA:

1. PR CI is green, including AI merchandising and deploy-wrapper workflows.
2. Latest `main` was checked immediately before merge.
3. Production deployment completed through the canonical wrapper and the deployed-head marker equals merged main.
4. `runtime-smoke.sh` reports both text and image smoke success using the actual MiniPC Codex session.
5. Scheduler is active as either `systemd-user` or the verified cron fallback.
6. A controlled WooCommerce E2E proves:
   - draft/pending -> publish creates a queue job;
   - the worker creates and applies a new verified thumbnail when imagegen succeeds;
   - one managed AI detail block is written to `post_content`;
   - supplier/base content remains outside that block;
   - a later supplier thumbnail repair/catalog update does not overwrite the successful AI thumbnail or managed detail block;
   - a deliberately failed Codex job leaves the supplier/base fallback unchanged.
7. Any synthetic QA product and generated test assets are cleaned up without touching real customer orders, payments or supplier fulfillment.

If runtime access is unavailable, report source/CI completion separately from production/runtime verification; never collapse those states into one success claim.
